说明链下数据被篡改也无法完成权属转移，链上校验是最后一道防线

四、本轮修复的两个关键问题

  • 底层 API 误用：client.sendTransaction(to, data, bool) 的第二个参数实为 nodeId， 传合约地址会报 -4010 no connection available。改用 SDK 高层封装 AssembleTransactionProcessor 解决。
  • 存证 ID 取值脆弱：原设计让合约自增 ID 再回读返回值，一旦 SDK 未解析出返回值会全部落成 -1， 导致 chain_record 主键冲突。改为链下雪花算法发号、连同哈希一起写链， 业务主键与链上账本 key 天然一致。

真实链受 PBFT 共识与出块间隔制约，单笔上链约需 538 ms，吞吐约为内存模拟的 1 / 1624。这一差距是「批量上链 + 异步化」优化策略的量化依据： 批量合并 N 笔为一次合约调用、业务写库后先返回再由异步任务补写回执， 可把用户感知延迟从 538 ms 降到毫秒级，而链上吞吐上限保持不变。
